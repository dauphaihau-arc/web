# Storefront visual regression

Pixel baselines for the surfaces a broken stylesheet would be noticed on. This
suite answers "did the layout change?" — it never replaces the journey
assertions in `e2e/`.

## What is covered

| Spec | Surface |
| --- | --- |
| `product.spec.ts` | Product detail above the fold |
| `cart.spec.ts` | Cart with one item, full page |
| `guest-orders.spec.ts` | Guest order lookup, full page |
| `login-dialog.spec.ts` | Header login dialog, viewport |

Deliberately excluded: pages whose data the shared E2E mocks do not model (home
rails, category listing). A screenshot of a page that silently falls through to
a real API is not reproducible, so those wait until the fixtures cover them.

## Run

```bash
# Compare against the committed baselines (needs Playwright's Chromium)
pnpm e2e:visual
```

`e2e:visual` serves the static build through `webServer`, so every run rebuilds
`.output/public` with a pinned environment (`API_BASE_URL=http://127.0.0.1:9`,
`API_VERSION=1`, empty `ASSET_HOST`). A local `.env` never participates: the
baselines must not depend on a developer's API host. The API base has to be a
closed port — an empty value makes the app's `/v/**` calls loop back into its own
prerender and leaves `.output/public` without client assets. Point the suite at an
already-served app with `E2E_BASE_URL=http://host:port` to skip the build.

## Why baselines are Linux-only

Playwright keys a snapshot by platform: the committed file is
`<arg>-chromium-linux.png`. Font rasterisation and subpixel rounding differ
enough between macOS and Linux that a laptop baseline fails on CI on the first
run.

Baselines are therefore generated by CI, never locally:
`.github/workflows/visual-baselines.yml` (`workflow_dispatch`) runs
`--update-snapshots=all` in the same Playwright image the comparison job uses,
then uploads `visual-baselines-linux`.

To update a baseline:

1. Run the **Visual baselines** workflow for your branch, optionally with the
   `spec` input (`cart.spec.ts`) to regenerate one surface.
2. Download the `visual-baselines-linux` artifact and replace
   `apps/storefront/e2e-visual/__screenshots__/`.
3. Review the changed PNGs — they are the layout diff you are approving — and
   commit them.

`__screenshots__/.gitignore` rejects `*-darwin.png` and `*-win32.png` so a local
`playwright test --update-snapshots` cannot leak into a commit.

## Determinism rules for new specs

Use `openVisualPage` / `waitForVisualReady` from `support/visual.ts`; they pin
what a raw `page.goto` leaves open:

- API responses come from `e2e/support/network.ts`, never the network.
- Cross-origin images are answered with a transparent pixel, every other
  cross-origin request is aborted. Same-origin build assets still load, including
  `_nuxt/fonts/*.woff2`; `document.fonts.ready` settles them, so a font change
  changes baselines and needs a regeneration.
- Color mode is forced to light, animations are disabled by the screenshot
  options, and `reducedMotion: 'reduce'` is set in the config.
- `waitForVisualReady` waits for a content marker, `document.fonts.ready`, a
  scroll pass that triggers reveal-on-scroll and lazy hydration, and
  `networkidle`. Never add a `waitForTimeout`.

Mask anything genuinely non-deterministic (timestamps, counters) with
`mask: [...]`. Do not raise `maxDiffPixelRatio` to silence a real diff — that is
the signal this suite exists for.
