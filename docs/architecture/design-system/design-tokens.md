# Design Tokens

Design tokens define the shared visual vocabulary for Arc Web. One module is the source of truth; everything else — Tailwind classes, CSS custom properties, and Nuxt UI theme values — is derived from it.

## Source Of Truth

`packages/ui/src/foundation/design-tokens.ts` exports:

- `designColors` — surface, border, state, text, media, rating
- `designRadii` — panel, dialog, chip, button
- `designShadows` — border, overlay, hero
- `designLayout` — page and shop layout metrics
- `sharedTailwindTheme` — the Tailwind `theme.extend` object
- `designTokenClasses` — class-name references used by `sharedAppConfig`

Never hardcode a value that a token already provides, and never add a token for a one-off screen.

## Outputs And Generation

The token module feeds two generated/serialized outputs:

| Output | Consumer |
|---|---|
| `sharedTailwindTheme` | `apps/<app>/tailwind.config.ts` |
| `:root` custom properties in `design-tokens.css` | `var(...)` consumers in `packages/ui` and app CSS |

`design-tokens.css` is generated by `packages/ui/scripts/generate-design-tokens.mjs` (`renderDesignTokensCss`). Never hand-edit it.

```bash
pnpm --filter @arc/ui generate:tokens
```

Drift is a test failure: `design-tokens.spec.ts` compares the committed CSS against the renderer output.

Color keys must stay kebab-case (`on-dark`, not `onDark`). Tailwind derives utility names from the key verbatim, so a camelCase key emits a class nobody uses; the spec rejects any camelCase key except `DEFAULT`.

The generated file holds variables only. Hand-written consumer rules live in `layout.css`, `elevation.css`, and `scroll.css`, all pulled in by `app-base.css`.

## Token Reference

| Group | JS export | CSS variables | Tailwind usage |
|---|---|---|---|
| Surface | `designColors.surface` | `--surface-*` (`default`, `subtle`, `muted`, `hover`, `control`, `keycap`, `accent`, `skeleton`, `inverse`, `overlay`, `overlay-dark`) | `bg-surface`, `bg-surface-subtle`, `bg-surface-hover`, `bg-surface-control`, `bg-surface-skeleton` |
| Border | `designColors.border` | `--border-subtle`, `--border-muted`, `--border-hover` | `border-border-subtle`, `border-border-muted`, `border-border-hover` |
| State | `designColors.state` | `--state-{success,neutral,warning,danger,info}-{surface,border,text}` | `bg-state-success-surface`, `border-state-danger-border`, `text-state-warning-text` |
| Text | `designColors.text` | `--text-muted`, `--text-subtle`, `--text-strong`, `--text-on-dark` | `text-text-muted`, `text-text-strong` |
| Media | `designColors.media` | `--media-product` | `bg-media-product` |
| Rating | `designColors.rating` | `--rating-star` | `text-rating-star` |
| Radius | `designRadii` | `--radius-panel`, `--radius-dialog`, `--radius-chip`, `--radius-button` | `rounded-panel`, `rounded-dialog`, `rounded-chip`, `rounded-button` |
| Shadow | `designShadows` | `--shadow-border`, `--shadow-overlay`, `--shadow-hero` | `shadow-border`, `shadow-overlay`, `shadow-hero` |
| Layout | `designLayout` | `--layout-*` | `max-w-home-layout`, `max-w-shop-layout`, `max-w-shop-layout-content`, `w-shop-layout-sidebar`, `p-page-gutter`, `bg-layout-shop` |

`designLayout` maps to fixed CSS variable suffixes (`--layout-max-width-home`, `--layout-shop-background`, …); the generator keeps those public names stable.

## Surface Ladder

Surfaces are ordered, not interchangeable:

| Step | Value | Token | Typical use |
|---|---|---|---|
| 0 | `#FFFFFF` | `surface` | page and card base |
| 1 | `#FAFAFA` | `surface-subtle` | recessed section |
| 2 | `#F4F4F5` | `surface-muted`, `surface-hover`, `surface-accent` | muted panels, white-surface hover |
| 3 | `#E4E4E7` | `surface-control`, `surface-keycap`, `surface-skeleton` | controls, keycaps, skeletons |

`surface-hover` is a white-surface hover; do not pair it with `surface-control`, which is already two steps down. `surface-inverse` (`#09090B`) is for inverted chrome; `surface-overlay` and `surface-overlay-dark` are translucent scrims.

## Color Rules

- Zinc is the only gray ramp. Semantic tokens already encode it.
- Reach gray through `bg-surface-*`, `border-border-*`, `text-text-*`, and `state-*`; never `gray-*`, `zinc-*`, `slate-*`, `neutral-*`, or `stone-*` in light mode.
- Raw palettes are allowed only as `dark:` variants, and dark mode accepts only `zinc`. There is no dark token layer.
- No new gray ramps, no one-off hex values, no `customGray`.
- State pairs are used together: `state-{name}-surface` for fill, `-border` for outline, `-text` for content.

## Nuxt UI Palette Pinning

Nuxt UI injects `--color-gray-50…950` from `ui.gray` and resolves its own `gray` classes against that palette. `design-tokens.spec.ts` therefore pins:

- `sharedAppConfig.ui.gray === 'zinc'`
- `border.subtle` to `zinc[200]`, `border.muted` to `zinc[300]`, `border.hover` to `zinc[400]`
- `surface.control` to `zinc[200]`, `surface.muted` to `zinc[100]`, `surface.subtle` to `zinc[50]`
- `text.muted` to `zinc[500]`, and the remaining text tones to their zinc steps

Changing either the palette or a semantic token without the other fails the test.

## Enforcement

`scripts/check-architecture.mjs` scans app source and `packages/ui/src` for:

- raw gray palette classes (`bg-gray-*`, `text-zinc-*`, …)
- raw gray CSS variables (`var(--color-gray-*)`)
- the retired `customGray` name

Only `packages/ui/scripts/` and the three design-token files are exempt. `dark:` variants may use zinc; any other palette under `dark:` is a violation.

```bash
pnpm check:architecture
pnpm test:packages
```
