# Visual Regression

Pixel baselines for the storefront surfaces where a stylesheet or layout change
is the incident. This layer answers "did the layout move?"; it never replaces the
journey assertions in `apps/storefront/e2e/`.

Runbook for the suite itself (spec list, helper contract, baseline mechanics):
`apps/storefront/e2e-visual/README.md`.

## What it covers

| Spec | Surface | Capture |
|---|---|---|
| `product.spec.ts` | Product detail | Viewport |
| `cart.spec.ts` | Cart with one item | Full page |
| `guest-orders.spec.ts` | Guest order lookup | Full page |
| `login-dialog.spec.ts` | Header login dialog | Viewport |

Four surfaces, not four pages of screenshots. A visual suite earns its keep only
while every diff is worth reading, so coverage grows one incident at a time.

Excluded today, because the shared E2E mocks do not answer the endpoints those
pages need: the home rails and the category listing. The product detail spec stops
at the fold because its shipping, review, and recommendation sections request
endpoints the fixtures do not model; a full-page capture would photograph
skeletons and fail on unrelated churn. Both gaps close when the fixtures cover
the responses, not by masking.

## Why baselines are Linux-only

Playwright keys a snapshot by platform, so the committed files end in
`-linux.png`. Font rasterisation and subpixel rounding differ enough between macOS
and Linux that a laptop baseline fails on CI on the first run, and a suite that
cries wolf on day one gets muted.

Consequences:

- Baselines are generated by CI, not by a developer machine: the `Visual
  baselines` workflow (`.github/workflows/visual-baselines.yml`) runs
  `--update-snapshots=all` inside `mcr.microsoft.com/playwright:v1.63.0-noble` and
  uploads the images as `visual-baselines-linux`.
- The `storefront-visual` gate runs in that same image rather than on a bare
  runner, so generation and comparison share one browser build and font stack.
- `apps/storefront/e2e-visual/__screenshots__/.gitignore` rejects `*-darwin.png`
  and `*-win32.png`, so a laptop `--update-snapshots` cannot leak into a commit.

## Determinism contract

Every spec goes through `openVisualPage` and `waitForVisualReady`
(`apps/storefront/e2e-visual/support/visual.ts`). They pin what a raw
`page.goto` leaves open:

- API responses come from `apps/storefront/e2e/support/network.ts`, never from a
  live API.
- Cross-origin images are answered with a transparent pixel and other
  cross-origin assets are aborted, so a CDN or webfont cannot change the capture.
- Color mode is forced to light, animations are disabled by the screenshot
  options, and the config sets `reducedMotion: 'reduce'`, `locale: 'en-US'`,
  `timezoneId: 'UTC'`, `deviceScaleFactor: 1`.
- The wait is a content marker, `document.fonts.ready`, a scroll pass that
  triggers reveal-on-scroll and lazy hydration, then `networkidle`. Never a
  `waitForTimeout`.

Images are always masked: they are already transparent pixels, and masking keeps
a shift inside an image slot out of the diff while the card, title, and price
around it still have to match.

## Tolerance

`threshold: 0.2` and `maxDiffPixelRatio: 0.01` absorb antialiasing on text and
borders while a shifted layout still fails. Retries are `0`: a retried diff either
hides a regression or doubles the noise.

When a diff is intentional, regenerate the baseline in the same PR as the UI
change, so the reviewed diff shows the change. When a diff is not intentional,
fix the layout — raising `maxDiffPixelRatio` or masking a moved element is how
this layer becomes decorative.

## Commands

From `apps/web`:

```bash
pnpm --filter @arc/storefront e2e:visual   # compare against the committed baselines
```

Regeneration has no local command on purpose: it runs in CI, where the renderer
matches the gate. See below.

## Regenerating a baseline

Dispatch **Visual baselines** (`.github/workflows/visual-baselines.yml`) for your
branch, optionally with the `spec` input to regenerate one surface. The job runs
`playwright test --update-snapshots=all` in the Playwright image and uploads
`visual-baselines-linux`; then:

1. Download the artifact and replace
   `apps/storefront/e2e-visual/__screenshots__/`.
2. Review the changed PNGs — that is the layout change being approved.
3. Commit them in the same PR as the UI change.

Generated baselines are a reviewed artifact, not a silent refresh: the round trip
is the cost of a suite whose comparison and generation run on one renderer.

## CI

Job `storefront-visual` in `.github/workflows/ci.yml`, gated by the `changes`
filter on storefront or shared-package edits. It runs inside the Playwright image
and uploads:

- `playwright-report-storefront-visual` — HTML report with the diff slider.
- `playwright-visual-diffs` on failure — the actual/expected/diff image triples.

Traces are off for this suite: the diff image is the artifact that explains a
visual failure, and trace zips written into a mounted volume under parallel
workers produce filesystem contention unrelated to layout.

## Adding a spec

1. Confirm the surface's data comes from `installStorefrontApiMocks`; if it does
   not, extend the fixtures first.
2. Use `test` from `support/visual.ts`, `openVisualPage`, then
   `waitForVisualReady` on a content marker that only renders real content.
3. Choose the capture deliberately: full page once every section is
   deterministic, viewport while any part of it still depends on unmocked data.
4. Mask only genuinely non-deterministic regions, and say why in a comment.
5. Generate the baseline by dispatching **Visual baselines** for the branch, then
   commit the `-linux.png` it produces.
